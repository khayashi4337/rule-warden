# ADR-0002: ルール条単位パーサーの設計

- 日付: 2026-10-06
- 状態: ドラフト（林さんレビュー待ち）
- 記録者: Devin
- 上位決定: ADR-0001 D1（制御単位はルール 1 条ずつ、隔離は物理移動）

## 目的

`C:\Users\user\.claude` 配下のルールファイルを **1 条単位** に分解し、
各条に安定した ID・出自・ロード状態を付与するパーサーの仕様を決める。
隔離・復元（物理移動）がこの条を単位として動作する。

## 用語

| 用語 | 意味 |
|---|---|
| 条（rule unit） | 管理・隔離・復元の最小単位。箇条書き 1 項目・段落・表の 1 行など |
| ロードグラフ | `CLAUDE.md` を起点に `@` 参照をたどって到達できるファイルの集合。AI のコンテキストに実際に入る範囲 |
| heading_path | 条が属する見出し階層を `"A > B"` のように連結した文脈情報 |
| content_hash | 条本文を正規化して sha256 にかけた先頭 16 桁。同じ文なら同じ値になる |
| surrogate id | 本文と無関係な連番の主キー（代理キー）。DB 内部での参照専用 |
| frontmatter | Markdown ファイル先頭の `---` で囲まれたメタデータ領域 |
| アンカー | 復元位置の目印。前後の条の content_hash を使う |
| atomic 書き込み | 一時ファイルへ全量書いてから rename で差し替える方式。読み手が半壊状態を見ない |
| fixture | テストで使う固定の入力データと期待値 |
| 負例 | 検査対象の性質だけを故意に壊した入力。検査が本当に失敗するか確認するために使う |
| 準ルール | `rules_junrule.md` にある、有効な規則から外した文の退避場所（人間による手動隔離の先例） |

## 対象実体の実測（2026-10-06）

| ファイル | git 管理 | @到達 | 構造 |
|---|---|---|---|
| CLAUDE.md | ○ | 起点 | `### N.` 節 + 箇条書き・番号付き・表・`@` 行 |
| rules_dots_charter.md | ○ | ○ | `## N.` 節 + 箇条書き（Dots 憲章） |
| rules_deep_think.md | × | ○ | 箇条書き中心 |
| PROFILE.md | × | ○ | 段落中心 |
| rules_explain.md / rules_paper.md / rules_git.md | × | ○（表セル内 `@`） | 箇条書き |
| rules_junrule.md | × | ×（明示的に非ロード） | `## 退避 N:` ブロック |
| RULES.md / FLAGS.md / MCP_*.md / MODE_*.md / PRINCIPLES.md 等 | × | × | 様々（非ロード＝事実上無効） |

実測から分かったこと:

- **git 管理は 4 ファイルのみ**（CLAUDE.md, rules_dots_charter.md,
  skills/codex-review/SKILL.md, 始末書）。大多数のルールファイルは untracked で、
  出自はファイルシステム時刻しか取れない。
- `@` インポート行は**行頭だけでなく表セル内にも現れる**（`| @rules_git.md |` 形式）。
  行頭マッチだけでは取りこぼす。
- `rules_junrule.md` は「CLAUDE.md から読み込まない」と書かれた、
  人間による手動隔離の先例。隔離フォルダの概念は既に存在する。

## 決定事項

各決定には「理由」を付記する。理由が変わったときは決定も見直す。

### P1. 条（rule unit）の定義

Markdown を構造解析し、以下を 1 条とする。

- **箇条書きのリーフ項目**（`-` / `*` / `+` / 番号付き）。
  継続行（次の箇条書き・見出しまでの字下げ行）はその条に含める。
- **見出し直下の独立段落**（箇条書きを持たない節の本文ブロック）。
- **表の 1 行**（表は行単位の条の集合として扱う。ヘッダ行は文脈）。
- **`@` インポート参照**（ロード制御を行う条として管理対象に含める。
  これを隔離すると参照先ファイル全体が非ロードになる）。

解析しないもの: コードフェンス内、HTML コメント内、引用符で囲まれた
「退避した文」のような**引用テキスト**（元の規則ではなく記録）。

**理由**:

- リーフ単位にするのは、隔離の目的が「疑わしいルールだけを外す」ことだから。
  節・ファイル単位だと健全な条まで巻き込んで無効化し、
  「汚染度を下げて自浄作用を取り戻す」目的（README）に反する。
- `@` 参照を条に含めるのは、**ファイル全体をロード状態から外せる
  スイッチ**がルール文と同じファイル内に同居しているから。
  管理対象外にすると「`@` 行だけ残して中身を隔離」という中途半端な
  状態を防げない。
- 引用テキストを除くのは、rules_junrule.md が示すように
  「元の規則を引用した記録」が存在するから。引用を条として扱うと
  同一文が二重に現れ、隔離しても引用側に残る=無効化失敗になる。

### P2. 子箇条書きの扱い

子 bullet は独立した条とするが、**親条の隔離は子孫を含む**（包含ルール）。
親だけを消すと子が宙に浮くため。リーフ条の隔離はその条の行範囲のみ除去する。

**理由**: 子 bullet は文脈として親を必要とする。親だけ消すと
「何についての項目か分からない断片」がファイルに残り、
隔離操作がファイルを壊す。逆に子だけを残す必要があるときは、
子を個別に復元すればよいので包含で問題ない。

### P3. 条 ID

- `norm_text` = 空白・改行を正規化した条本文
- `content_hash` = sha256(norm_text) の先頭 16 hex
- DB 上の主キーは surrogate id。`content_hash` + `file_path` + `heading_path` で
  実体を識別する。
- 本文が編集されると content_hash が変わる = 新しい条として現れる。
  前版との対応付けは「同ファイル・同見出しパス・位置近傍・テキスト類似度」で
  行う（追跡ロジックは実装時に決定。ここでは「hash が変わると別条」だけ確定）。

**理由**:

- 内容ハッシュにするのは、**位置ベースの ID が並べ替えで全滅する**から。
  ルールの条は順序入替・別ファイル移動が普通に起きる。
  「同じ文なら同じ ID」であれば移動を跨いで追跡できる。
- 正規化するのは、インデントや改行位置の揺れで「同じ条」が
  別 ID になるのを防ぐため。
- surrogate id を別途持つのは、content_hash が編集で変わることを
  前提にした設計のため。「DB 上の連番」と「条の同一性」を分離しておくと、
  外部キー（ステータス履歴等）が編集のたびに張り替えにならない。
- 「hash が変わると別条」と割り切るのは、同一性を推定で誤認する
  リスクより「新しい条として審査し直す」方が安全側だから。
  逸脱した AI がルールを少しだけ書き換えた場合、それを「同じ条の更新」と
  見なすと旧条の承認が引き継がれてしまう。

### P4. ロードグラフ

- 起点: `CLAUDE.md`
- `@<path>` 参照を**行内の任意位置**から抽出（表セル内を含む）。
  相対パスは参照元ファイルのディレクトリ基準で解決。
- 抽出したパスが実在し再帰的に到達可能 = **有効（loaded）**。
  到達不能なルールっぽい `.md` = **非ロード**として別枠で一覧化
  （rules_junrule.md のような意図的隔離と、単なる残骸を区別する材料にする）。

**理由**: AI のコンテキストに実際に注入されるのはロードグラフ上の
ファイルだけであり、**汚染として問題になるのは有効ルールだけ**。
非ロードのファイルを有効なものと同列に採点すると、審査負荷が無駄に
増える。ただし非ロードファイルも完全には無視しないのは、
AI が「隔離すべき条を非ロードファイルに移して隠す」という逃げ道を
塞ぐため。別枠で一覧は維持する。

### P5. 出自（provenance）の 2 系統

| git 管理 | 出自の取り方 |
|---|---|
| ○ | `git log -L` 相当で条テキストの初出コミット・直近変更コミット・作者を取得 |
| × | ファイルの作成日時・更新日時のみ。「履歴なし」と明示する |

「出自が取れない」こと自体を汚染の兆候情報として表示に載せる
（AI が勝手に作ったファイルは git 未登録になりやすい）。

**理由**: 実測で git 管理は 4 ファイルのみと判明したため、
「git 履歴前提」の出自設計は大多数のファイルで機能しない。
一方で untracked でも「いつ現れたか」はファイルシステム時刻で分かる。
さらに、追跡不能な出自は**単なる情報不足ではなく兆候**として扱う:
林さんの承認フローを通った変更は普通 git に残るので、
履歴の無いルールは「承認外の経路で入った」可能性を示す。

### P6. 隔離の物理形式

```
.claude/
  quarantine/
    <原ファイル名>/
      <content_hash>.md      # 条本文（原文のまま）
```

各隔離ファイルの先頭に YAML frontmatter を付ける:

```yaml
---
source_file: CLAUDE.md
heading_path: "🔴 核心ルール > 2. 止まるタイミングを間違えない"
ordinal: 3                # 同見出し内での条の出現順
content_hash: ab12cd34ef56...
prev_unit_hash: ...       # 復元時の前アンカー（無ければ null）
next_unit_hash: ...       # 復元時の後アンカー
quarantined_at: 2026-10-06T13:00:00+09:00
reason: <隔離理由>
---
```

隔離先は `.claude` git リポジトリ内に置き、移動が git 差分として残る（D1）。

**理由**:

- 1 条 1 ファイルにするのは、隔離・復元を**ファイル移動**という
  副作用の少ない操作で実現するため。DB 内に隔離本文を持つと
  「ファイル上の操作」と「DB 上の状態」が乖離しやすい。
- frontmatter に復元情報を同梱するのは、隔離ファイル自体を
  **自己完結した記録**にするため。DB が壊れても quarantine/
  だけ見れば何をどこへ戻せばよいか分かる。
- git リポジトリ内に置くのは、隔離・復元という**ルールへの介入そのもの
  を監査可能にする**ため。隔離は無断でも実行されうる操作なので、
  diff と履歴に残す（D1 の意図）。

### P7. 復元

1. quarantine ファイルの frontmatter から `source_file` とアンカーを読む
2. 対象ファイル内で `prev_unit_hash` / `next_unit_hash` の条を探し、その間に挿入
3. アンカーが見つからない（周辺が編集済み）場合は見出しパスの末尾に挿入し、
   「位置ずれあり」を記録する

**理由**: 行番号・位置ベースの復元は、隔離中に周辺が編集されると
間違った場所に挿入する。前後の条のハッシュをアンカーにすれば、
周辺が動いていても意味のある場所（同じ隣接条の間）に戻せる。
アンカー喪失時に見出し末尾へ退避するのは、位置を誤って挿入する
リスクより「場所が変わった」と記録して人に判断を委ねる方が安全だから。

### P8. 書き戻しの性質

- 隔離・復元ともに**対象ファイル全体の書き戻し**ではなく行範囲の除去/挿入。
  原文の改行コード・インデント・空白を一切変更しない（git diff を最小にする）
- 書き戻しは atomic に（一時ファイルへ書いて rename）

**理由**:

- diff を最小にするのは、**パーサー自身の操作痕跡をルール変更と
  区別可能にする**ため。整形まで diff に乗ると「誰が何を変えたか」の
  監査が機能しない。
- atomic にするのは、書き込み途中の中断で**有効ルールファイルが
  半壊する**事態を防ぐため。CLAUDE.md は次のセッション開始時に
  そのまま AI のコンテキストに入るので、中途半端な状態のファイルは
  それ自体が汚染源になる。

### P9. 実装方針

- 行ベースの独自パーサで実装する（依存を増やさない）。
  対象構造は見出し・リスト・表・フェンス・`@` 行で十分に表現できる。
- 言語はアプリ本体のスタック確定時に合わせる（本 ADR は言語非依存の仕様）。
- fixture として現行ファイル群のスナップショットを使い、
  「条数」「各条の行範囲」「ロードグラフ」の期待値を固定テストにする。
  負例: フェンス内の偽 bullet、壊れた @ 参照、空ファイル、BOM/UTF-16。

**理由**: Markdown ライブラリを使わないのは、汚染監視ツールが
**外部依存の供給網に信頼を置く設計を避ける**ため（プロジェクトの
前提と整合）。必要な構造は行単位で判定可能で、完全な Markdown
準拠は不要（実データに現れる構造だけ正確に扱えばよい）。
